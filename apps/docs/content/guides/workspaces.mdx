# Workspaces

A workspace is one git branch of a repository, running in its own sandbox with
its own dev server, frames, agent chats, and terminals. The sidebar's
**Workspaces** section lists every workspace on the canvas in one flat list,
by title. Wherever a workspace is named, on a row, a group or frame label, or
the address bar, it shows the same way: an icon for what it's doing, its
title, and its pull request when there's room.

## Creating workspaces

Click **+** (**New workspace**) next to **Workspaces** in the sidebar.
**Create workspaces** can create several at once:

<Screenshot name="new-workspace-multi" alt="Create workspaces with two rows, each with a prompt" />

- Each row starts from a **base branch** (the chip above the prompt), which
  defaults to the repository's default branch.
- On a canvas with several repositories, each row also has a **repository**
  chip beside the base branch. It starts on the repository you used last;
  picking another resets the base to that repository's default branch.
- Type a **prompt** to give the new workspace its first task. It's sent to
  the agent as soon as the sandbox is ready, and the agent titles the
  workspace from it in sentence case (for example "Add pricing FAQ") and
  names its branch from the same words (`add-pricing-faq`). Leave the prompt empty to create a bare
  workspace with a generated name; its first chat message titles it.
- Each row has its own model picker and **Plan** toggle, the same as the
  [chat composer](/guides/agent#the-composer).
- **Add another** (<kbd>⌘</kbd> <kbd>↵</kbd>) adds a row. <kbd>↵</kbd> creates
  them all.

A new workspace goes through **creating** and **starting** while it checks
out the branch, runs the setup script, and boots the dev server. The agent
panel shows the live **sandbox logs** meanwhile. When the server is up, a
frame appears on the canvas and the panel switches to chat.

To work on a branch that already exists, click the **…** next to **+** and
choose **Open existing git branch** (on a canvas with several repositories,
pick the repository first).

A canvas with no repository yet says that workspaces need one, with an
**Add repository** button that opens Canvas settings on
[Repositories](/guides/repositories).

## Titles

A workspace is named by its title everywhere: the sidebar, the agent panel's
picker, the canvas list and each frame's workspace badge and address bar. The
agent writes it from the first message in the workspace's first chat, the
same way it names the chat. Later chats never change it.

Renaming a workspace (double-click its title, or **… → Rename**) changes only
the title, so it never touches the branch, its pull request or anyone's
checkout. To rename the branch itself, use **… → Rename branch…**.

## The sidebar row

<Screenshot name="canvas-overview" alt="The canvas sidebar: the flat Workspaces list above, the Canvas layers list below" />

Each workspace row shows:

- a **status icon** for what the workspace is doing: a spinner while it
  starts, an activity spinner while the agent works, a small circle when it's
  ready, a dashed circle when it's stopped, a check circle when it's
  [done](#marking-a-workspace-done), or a warning when setup failed.
  Click the warning for the error, with **Retry**, **Recreate** and
  **Copy error**;
- the workspace's **title** (double-click to rename). Workspaces created
  before titles existed show their branch name until you rename them;
- at the end, the workspace's **pull request** as a small outlined badge:
  its icon in GitHub's colours (green open, purple merged, red closed) and
  its number. When the row is too narrow for both, the badge is hidden
  rather than cutting off the title. With no pull request the row shows
  **+/− line counts** for changes compared with the base branch. A workspace
  that's starting, stopped or failed shows neither;
- on a canvas with two or more repositories, the **repository's short name**
  at the end, so you can tell web and API work apart. With one repository
  it's never shown.

The agent panel's header and its picker, a frame's workspace list and the
**Remove** repository dialog show a workspace the same way: the status icon,
then the title, then the pull request badge (the header keeps its own pull
request button instead).

Workspaces keep their repository's order, and within it the order you give
them: drag a row to move it among its repository's workspaces.

### Sorting and grouping

<Screenshot name="ws-list-view" alt="The Workspaces list's … menu with the Sort by submenu open" />

The **…** beside **Workspaces** sets how the list is shown:

- **Sort by** shows the current sort; pick **Manual** (the order you drag,
  and the default),
  **Recent activity** (the workspace whose agent was last asked something
  first; one that never ran a turn counts from when it was created) or
  **Name**. Rows drag only in **Manual** order with grouping off.
- **Group by state** splits the list into **Working** (the agent is working
  or setup is running), **Needs you** (setup failed, or its pull request is
  open) and **Idle** (ready or stopped). Each section gets its own heading in
  place of **Workspaces**, and rows inside it follow the sort you picked.
  Empty sections are hidden.

[Done](#marking-a-workspace-done) workspaces stay in their own section at the
bottom whatever you pick. The choice is yours alone: it's remembered for each
canvas in this browser, and collaborators keep their own.

Click a row to make it the agent panel's target. Double-click to also open
the panel.

Hover a row to see where the workspace is used: the canvas list lights up the
[groups](/guides/canvas#a-groups-workspace) on it and the frames that show
it, and the canvas outlines those frames. It works the other way too:
hovering a group, a frame, or a group's workspace lights up its
workspace's row.

### The hover card

Hover a workspace row, or a workspace named on a group or frame label or in
the address bar, to see its details:

- its title and what it's doing now, such as the setup step and how long it
  has taken, that the agent is working, or that it's ready, stopped or done;
- its **repository**, its **git branch**, the **base** branch its changes are
  compared with, and its **changes** as +/− line counts.

This is where you find a workspace's branch name, since rows and labels show
its title.

## The workspace menu

Hover a workspace and click **…**. The menu starts with the one action the
workspace's state calls for (**Retry setup** after a failed setup, the pull
request, **Reopen** on a done workspace, or **Open prototype player**), then groups the rest under **View**,
**Git** and **Manage**:

<Screenshot name="ws-menu" alt="The workspace menu" />

| Item | What it does |
| --- | --- |
| **Open prototype player** | Opens [play mode](/guides/play-mode) for this workspace. |
| **Open in browser** | Opens the dev server in your browser. On desktop this is a stable URL like `http://my-branch.my-app.localhost:1355`. |
| **Show all routes** | Adds a group with one frame per route the workspace has visited. |
| **Create pull request** / **Open pull request #N** | Opens a PR into the repository's default branch, or jumps to the existing one. |
| **Rebase on *main*** | Asks the agent to rebase onto the latest default branch. It runs as a chat turn, so the agent can walk through any conflicts with you. |
| **Open branch on GitHub** | Opens the branch on GitHub. |
| **Rename branch…** | Renames the git branch, on GitHub and in the workspace. Names already used on the remote are refused. The workspace keeps its title. |
| **New workspace from here…** | Opens **Create workspaces** with this workspace's branch as the base. |
| **Rename** | Renames the workspace's title. The git branch stays as it is. |
| **Restart** | See [Restarting](#restarting). |
| **Mark as done** / **Reopen** | See [Marking a workspace done](#marking-a-workspace-done). |
| **Delete** | Removes the workspace, and optionally its branch on GitHub. |

## Restarting

When a preview gets stuck, **Restart** offers escalating fixes:

<Screenshot name="ws-restart" alt="The Restart submenu: Restart dev server and Recreate from scratch" />

- **Restart dev server** restarts only the dev server process. It's quick,
  keeps every file, and works even while the agent is busy. Try it first.
- **Restart sandbox** *(hosted)* restarts the whole sandbox VM. Your working
  tree, including uncommitted changes, is restored from a snapshot.
- **Recreate from scratch** deletes the sandbox and checks the branch out
  fresh. **Uncommitted changes are permanently discarded**, so you'll be asked
  to confirm.

<Screenshot name="recreate-dialog" alt="The Recreate from scratch confirmation" />

<Callout type="warning">
  On the hosted app, sandboxes are ephemeral VMs that are reclaimed when idle.
  Anything worth keeping has to be committed and pushed. The agent commits
  after every change for this reason. On desktop, worktrees live on your disk
  and survive restarts.
</Callout>

## Marking a workspace done

When you're finished with a workspace, **… → Mark as done** puts it away
without deleting anything:

- its dev server stops;
- its frames leave the canvas. A group on the workspace hides whole, and a
  frame on it inside another group hides on its own;
- its row moves into a collapsed **Done** section at the bottom of the
  Workspaces list, with a check circle for its status icon;
- its chats and history stay, and frame workspace lists stop offering it.

Everyone on the canvas sees it as done. It isn't available while the agent is
working. Merging its pull request doesn't mark a workspace done; only the menu
does.

To bring one back, open **Done** and choose **… → Reopen**. The workspace
starts again and its frames return where they were.

## Pull requests

There are three ways to open a PR:

- **Create PR** in the agent panel header. It opens the PR directly, using
  the branch's commit messages for the title and body, and the button then
  turns into a link to it.
- **Create pull request** in the workspace menu.
- Ask the agent ("open a PR for this"). It uses its `create_pr` tool and shows
  a link card in the chat.

PRs target the repository's default branch. The PR's state (open, merged, or
closed) is shown at the end of the workspace row and on the header button. Creating PRs
needs a GitHub connection.

## Deleting

**… → Delete** removes the workspace, its chats and its frames from the
canvas, and shuts down its sandbox. The dialog lists what it **Removes** and
what it **Keeps** (the git branch itself isn't deleted), and warns when
uncommitted changes, or on the hosted app unpushed commits, would be lost. If
you're connected to GitHub and the repository has a GitHub remote, it also offers
**Also delete the branch on GitHub**, which also closes an open PR. It's off
by default. If the remote
delete fails, the workspace is still deleted and a warning names the branch
left on the remote.

<Screenshot name="delete-branch-dialog" alt="The Delete workspace dialog with the Also delete the branch on GitHub option" />

## One branch, one workspace (desktop)

On desktop, every workspace is a git worktree of one shared clone, and git
allows each branch to be checked out only once. Opening a branch that's
already open in another workspace, or checked out in your own clone, fails
with a clear error rather than sharing the checkout. On the hosted app each
sandbox is an independent clone, so there's no such limit.
