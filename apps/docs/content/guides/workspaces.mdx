# Workspaces

A workspace is one git branch of a repository, running in its own sandbox with
its own dev server, frames, one agent chat, and terminals. A workspace and its
chat share one title. The **Chats** button at the top right of the Coordinator
opens the list of every chat on the canvas, by title. Wherever a workspace is named, on a row or a group or frame label, it shows the same way: an icon for what it's doing, its
title, and its pull request when there's room.

## Creating workspaces

Every new chat gets its own workspace. There are two ways to start one:

- **Draw a frame** with the **Frame** tool (<kbd>F</kbd>) and type what it
  should show. A new chat starts on the repository you used last, from its
  default branch (see [Frames](/guides/frames)).
- **Ask the Coordinator.** It picks the repository and the branch to start
  from, and can start several chats at once.

The agent titles the workspace from your first message in sentence case (for
example "Add pricing FAQ") and names its branch from the same words
(`add-pricing-faq`).

A new workspace's frame appears on the canvas straight away, and the canvas
zooms to it. The workspace goes through **creating** and **starting** while
it checks out the branch, runs the setup script, and boots the dev server.
To watch it happen, open **Dev server** under the workspace's composer (see
[Terminals](/guides/agent#terminals)). When the server is up, the frame shows
the app.

Every chat starts on a branch of its own, so two agents never push to the
same branch. To build on a branch that already exists, ask the Coordinator to
start a chat from it: the new chat starts from that branch on a new one.

A canvas with no repository yet says that workspaces need one, with an
**Add repository** button that goes straight to
[adding one](/guides/repositories#adding-a-repository).

## Titles

A workspace is named by its title everywhere: the Chats menu, the agent
panel's header, the canvas list and each frame's workspace badge and address
bar. Titles are in sentence case, like "Add pricing FAQ". Where a title comes
from depends on how the workspace started:

- **From a frame or a new repository**, the first message in the
  workspace's chat titles it and renames its branch to match (for
  example `add-pricing-faq`). If that branch name is already taken on the
  remote, a numeric suffix is added.
- **From a Coordinator plan**, the workspace takes the title from the plan,
  and its branch is named from that title when it's created. Its first
  message renames neither.

Earlier chats on a canvas from before workspaces had one chat keep their own
names and never change the workspace's title or branch.

Renaming a workspace (**… → Rename**, then type over its title) changes only
the title, so it never touches the branch, its pull request or anyone's
checkout. The branch keeps the name it was given. To rebase it or rename it,
ask the agent in its chat.

## The Chats menu

<Screenshot
  name="workspaces-menu"
  alt="The agent panel's Chats menu open: each chat with + and …"
/>

The **Chats** button sits at the far right of the
[Coordinator](/guides/coordinator)'s header, the agent panel's top
level. In a workspace, click **Coordinator** in the header to get back to it.
An orange dot on the **Chats** button means a workspace needs you: its setup
failed, its plan waits for your approval, its agent
[asked you a question](/guides/agent#questions), or its pull request can't
merge. An open pull request waiting on review doesn't count.
Click it (or Tab to it and press <kbd>↵</kbd>) to open the menu:

- a **search** field that finds a chat by its title or its workspace's
  branch, including done ones;
- **+** and **…** beside the search field, which stay there while you
  search;
- the **Chats** list, one row for each workspace's chat;
- under **No repository**, any
  [chats with no repository](/guides/agent#chats-with-no-repository).

On a canvas with no repository the menu lists only chats with no repository,
and **+** beside the search field starts one.

Pick a row to open that chat; the menu closes. <kbd>Esc</kbd> or a click
outside closes it without picking. The arrow keys move through the rows.
With the agent panel collapsed (<kbd>⌘</kbd> <kbd>I</kbd>), open the panel
first.

Each chat row shows:

- a **status icon** for what the workspace is doing: a spinner while it
  starts, an activity spinner while the agent works, an orange dot when it
  needs you (a plan to approve, a question to answer, or a pull request that
  can't merge), a small
  circle when it's ready, a dashed circle when it's stopped, a check circle
  when it's [done](#marking-a-workspace-done), or a warning when setup failed.
  Click the warning for the error, with **Retry**, **Recreate** and
  **Copy error**;
- the chat's **title**, which is its workspace's title, never its branch. A
  workspace without one (created before titles
  existed, or not asked anything yet) reads **New chat** until you
  rename it or its first chat message names it;
- at the end, the workspace's **pull request** as a small outlined badge:
  its icon in GitHub's colours (green open, purple merged, red closed) and
  its number. When the row is too narrow for both, the badge is hidden
  rather than cutting off the title. With no pull request the row shows
  **+/− line counts** for changes compared with the base branch. A workspace
  that's starting, stopped or failed shows neither;
- on a canvas with two or more repositories, the **repository's short name**
  at the end, so you can tell web and API work apart. With one repository
  it's never shown.

The agent panel's header, a frame's workspace list and the
**Remove** repository dialog show a workspace the same way: the status icon,
then the title, then the pull request badge (the header keeps its own pull
request button instead).

### Order

The list is grouped by state: **Working** (the agent is working or setup is
running), **Needs you** (setup failed, a plan waits for your approval, a
question waits for your answer, or its pull request can't merge) and **Idle**
(ready or stopped, including a pull request waiting on review). Each section
gets its own heading, and empty sections are hidden.

Inside each section, the workspace whose agent was last asked something
comes first; one that never ran a turn counts from when it was created.
[Done](#marking-a-workspace-done) workspaces stay in their own section at the
bottom.

Hover a row to see where the workspace is used: the canvas list lights up the
[groups](/guides/canvas#a-groups-workspace) on it and the frames that show
it, and the canvas outlines those frames. It works the other way too: while
the menu is open, hovering a group, a frame, or a group's workspace lights up
its workspace's row.

### The hover card

Hover a workspace row, the workspace's name in the agent panel's header, or a
workspace named on a group or frame label, to see its
details:

- its title and what it's doing now, such as the setup step and how long it
  has taken, that the agent is working, or that it's ready, stopped or done;
- its **repository**, its **git branch**, the **base** branch its changes are
  compared with, and its **changes** as +/− line counts.

This is where you find a workspace's branch name, since rows and labels show
its title.

## Workspace actions

Click **…** after the workspace's name in its chat header, or hover its chat
in the Chats menu and click **…**. A frame's **… → Chat** submenu holds
the same menu. It starts with the one action the workspace's state calls for
(**Retry setup** after a failed setup, **Mark as done** once its pull request
has merged, the pull request, **Reopen** on a done workspace, or **Open
prototype player**), then the rest, with dividers between
viewing, git and managing actions:

<Screenshot name="ws-menu" alt="The chat menu" />

| Item                                               | What it does                                                                                                         |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| **Open prototype player**                          | Opens [play mode](/guides/play-mode) for this workspace.                                                             |
| **Open in browser**                                | Opens the dev server in your browser. On desktop this is a stable URL like `http://my-branch.my-app.localhost:1355`. |
| **Show all routes**                                | Adds a group with one frame per route the workspace has visited.                                                     |
| **Create pull request** / **Open pull request #N** | Opens a PR into the repository's default branch, or jumps to the existing one.                                       |
| **Rename**                                         | Renames the workspace's title. The git branch stays as it is.                                                        |
| **Restart**                                        | See [Restarting](#restarting).                                                                                       |
| **Mark as done** / **Reopen**                      | See [Marking a workspace done](#marking-a-workspace-done).                                                           |
| **Delete**                                         | Deletes the chat with its workspace and frames, and optionally its branch on GitHub.                                 |

## Restarting

When a preview gets stuck, **Restart** offers escalating fixes:

<Screenshot
  name="ws-restart"
  alt="The Restart submenu: Restart dev server and Recreate from scratch"
/>

- **Restart dev server** restarts only the dev server process. It's quick,
  keeps every file, and works even while the agent is busy. Try it first.
  To stop the dev server instead, see
  [Running and stopping the dev server](/guides/agent#running-and-stopping-the-dev-server).
- **Restart sandbox** _(hosted)_ restarts the whole sandbox VM. Your working
  tree, including uncommitted changes, is restored from a snapshot.
- **Recreate from scratch** deletes the sandbox and checks the branch out
  fresh. **Uncommitted changes are permanently discarded**, so you'll be asked
  to confirm.

<Screenshot
  name="recreate-dialog"
  alt="The Recreate from scratch confirmation"
/>

<Callout type="warning">
  On the hosted app, sandboxes are ephemeral VMs that are reclaimed when idle.
  Anything worth keeping has to be committed and pushed. The agent commits after
  every change for this reason. On desktop, worktrees live on your disk and
  survive restarts.
</Callout>

## Marking a workspace done

When you're finished with a workspace, **… → Mark as done** puts it away
without deleting anything:

- its dev server stops;
- its frames leave the canvas. Documents and other workspaces' frames in the
  same group stay where they are;
- its row moves into a collapsed **Done** section at the bottom of the
  Workspaces list, with a check circle for its status icon;
- its chat and history stay, and frame workspace lists stop offering it.

Everyone on the canvas sees it as done. It isn't available while the agent is
working. Merging its pull request doesn't mark a workspace done, but once it
has merged, **Mark as done** moves to the top of the menu.

A toast says how many frames were hidden. Its **Undo** reopens the workspace
straight away. Later, open **Done** and choose **… → Reopen**. The workspace
starts again and its frames return where they were.

## Pull requests

There are three ways to open a PR:

- **Create pull request** in the agent panel header. It opens the PR directly, using
  the branch's commit messages for the title and body, and the button then
  turns into a link to it.
- **Create pull request** in the chat menu.
- Ask the agent ("open a PR for this"). It uses its `create_pr` tool and shows
  a link card in the chat.

PRs target the repository's default branch. The PR's state (open, merged, or
closed) is shown at the end of the workspace row and on the header button.
**Create pull request** shows only when the repository is on GitHub and
you're connected to GitHub, and it's available once the workspace has changes
to propose.

## Deleting

**… → Delete** deletes the chat, its workspace and its frames, and shuts down
its sandbox. The dialog says in a sentence what's deleted and that the git
branch stays, and warns when uncommitted changes, or on the hosted app
unpushed commits, would be lost. If
you're connected to GitHub and the repository has a GitHub remote, it also offers
**Also delete the branch on GitHub**, which also closes an open PR. It's off
by default. If the remote
delete fails, the workspace is still deleted and a warning names the branch
left on the remote.

<Screenshot
  name="delete-branch-dialog"
  alt="The Delete chat dialog with the Also delete the branch on GitHub option"
/>

Documents and mockups the chat made stay on the canvas. Any other chat can
then change them, and the first one that does takes them over.

## One branch, one workspace (desktop)

On desktop, every workspace is a git worktree of one shared clone, and git
allows each branch to be checked out only once. Opening a branch that's
already open in another workspace, or checked out in your own clone, fails
with a clear error rather than sharing the checkout. On the hosted app each
sandbox is an independent clone, so there's no such limit.
