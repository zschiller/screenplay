# Frames

A frame is a live preview of a workspace's dev server. It's a real browser
view, so hot reload, client-side routing, and app state all work as normal.

## Adding frames

- A new workspace gets a frame automatically once its dev server is up.
- The **Frame** tool (<kbd>F</kbd>) drops a 1280×800 frame where you click,
  or draws one where you drag. As you let go, the frame asks what it should
  show. Type what to build and press <kbd>Enter</kbd> (<kbd>Shift</kbd>
  <kbd>Enter</kbd> for a new line). The frame's size is sent along as the
  viewport, so a phone-sized frame gets a mobile layout. A frame shows a
  workspace, and a workspace needs a repository, so on a canvas with no
  [repository](/guides/repositories) the Frame tool is off until you add one.
- The chip beside **Send** says who answers. With nothing selected it's
  **New chat**: a new chat starts on it, and its workspace boots in that
  frame. If you had a frame, mockup or document selected when you drew, it's
  that layer's workspace instead: the frame shows that workspace, and your
  message goes to its chat, as if you'd sent it there (see
  [Sending while the agent works](/guides/agent#sending-while-the-agent-works)).
  Click the chip to switch between **New chat** and any workspace.

  <Screenshot
    name="frame-ask-answerer"
    alt="A frame drawn with the Home frame selected: the chip names the Home frame's workspace, and its menu lists New chat and every workspace"
  />

- Press <kbd>Esc</kbd> or click elsewhere to skip the question. The frame
  stays and shows **No workspace**. Click **Start a chat** in it to ask again,
  or pick a workspace for it from its title (**Choose a workspace**).

  <Screenshot
    name="frame-ask"
    alt="A frame just drawn, asking what it should show, with the New chat chip beside the Send button"
  />

  <Screenshot
    name="frame-unanswered"
    alt="A frame with no workspace, offering Start a chat"
  />

- **Show all routes** in the workspace menu adds a group with a frame for
  every route the workspace has visited.

## The title bar

Above each frame:

- **Name**: double-click to rename.
- **Workspace**, with its state icon, unless its
  [group](/guides/canvas#a-groups-workspace) names it because every frame in
  the group shows the same one. Click it to switch the frame's workspace.

Under the selected frame, an address bar shows its workspace and route. Click
the workspace to point this frame at another one, keeping its route and
state; this is how you compare workspaces on the same screen. Picking one
that differs from the other frames in its group moves the workspace from the
group's title onto each frame's. Click the route to edit
it in place, like a browser's address bar: type any path and press **Enter**, or
pick a route the workspace has visited from the list under the bar. **Esc**
puts the route back. Routes you visit while interacting
are added to the list automatically.

The route and scroll position are shared: when anyone viewing the canvas
navigates a frame, everyone else's copy follows. Your copy changes page
through the app's own router (Next's router, or the history API for React
Router, Vite and similar apps), so anything you typed or opened in the frame
stays put. Only a page with no client-side router reloads onto the new route.

## The frame toolbar

When exactly one frame is selected, a toolbar like a browser's appears under
it. From left to right:

| Button                | What it does                                                                                                                                                                                                                                                                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Back**, **Forward** | Step through the routes this frame has shown.                                                                                                                                                                                                                                                                                                         |
| **Address**           | The frame's workspace and route. Click the route to type a new one. **Reload** reloads the preview, and spins in its place while the page loads. A dot at the start of the address means the dev server disconnected or the preview failed.                                                                                                           |
| **Record flow**       | Like Interact, but every time you navigate, a snapshot of the previous page is left behind in the group. Clicking through a signup therefore lays the whole flow out as a row of screens. The address turns red with a screen count while recording.                                                                                                  |
| **Interact**          | Lets the frame take your clicks and scrolls, so you can use the app. The canvas stops panning over it, though <kbd>Space</kbd>-drag outside it still pans. ### Who's driving

One party drives a frame at a time, and only the driver's clicks and keys
reach it. Interact is the driver's seat: pressing it makes you the driver,
and leaving it lets go.

When the agent drives a frame, the frame shows it:

- **Agent has control** sits on the frame's title line, at its right edge.
- An unselected frame gets a 2px ring, so you can spot it
  from across the canvas.
- Selected, the Interact button shows the agent's dots instead of the cursor,
  and the frame has no resize handles, so its size can't change under it.

### Live frames

On a hosted canvas, each frame starts as your own copy: a preview running in
your browser, as fast as any page. Your copy follows the canvas: when someone
navigates the frame, or changes its [shared state](#shared-state) or Knobs,
every copy follows.

To look at the very same page with someone, click **Go live** (the broadcast
button after **Interact** in the frame's toolbar). The frame's browser starts
in its workspace's sandbox, on the frame's current page, and you're on it.
Nobody else is pulled in: everyone else keeps their own copy, and the frame's
title line reads **Live** for all of you. Anyone can click **Go live** on that
frame to join it, and then you all watch one browser, so when one of you
clicks through the page the others see it happen.

The **Go live** button stays filled while you're on the live frame. Click it
again to leave: you're back on your own copy, on the live frame's page, with
its cookies and local storage. What the page held only in memory, like a half
typed form, doesn't come along. If you open the canvas while a frame is live,
you land on it live. Once you leave a frame, you stay on your own copy for the
rest of your visit, until you click **Go live** again. When the last person
leaves, or closes their tab, the frame stops being live.

On your own copy, **Interact** works on your copy alone. On a live frame,
whoever has control is the only one whose clicks, keys and scrolling reach
it. Press Interact on a live frame nobody controls to take control. On one
someone else controls, nothing you do reaches the page: its title line says
who has control instead of **Live**, and the Interact button shows their
avatar. Leaving a live frame you control lets go of control first.

#### Asking for control

To take a turn on a frame someone else controls, click the Interact button
(its tooltip says **Click to ask for control**). The person with control sees
your ask under their Interact button and picks **Give control** or **Not
now**. When they give you control, the frame is yours and you're interacting
with it. Click the button again to take your ask back.

<Screenshot
  name="frame-control-requests"
  alt="Under the Interact button, Ana asks for control and Ben asks for control, each with Not now and Give control"
/>

When several people ask at once, the driver sees each of them and picks one;
the others keep waiting. When the driver leaves Interact, control passes to
whoever asked first. A driver who reloads the page or drops their connection
keeps control for 5 seconds. If they don't come back, control passes to
whoever asked first and is still here, or to nobody.

A live frame streams at up to twice its size, so it stays sharp when you zoom in
to 200%. When a workspace's sandbox goes to sleep, its frames' browsers stop
with it; when it wakes up, each frame reopens at the page it was on.

Comment pins, Knobs, the element picker and **Fit to content** work on a
live frame as on any other. A pin sits on the same element for everyone, and
a Knob you change shows in the one live page, so everyone on it sees it at once.

A live frame's Knobs also have a **Theme** knob, above the page's own, that
switches the page between **Light** and **Dark**. It sets what the page's
`prefers-color-scheme` matches, for everyone watching. A new frame starts in
Light. A preview running in your own browser, like your own copy or a frame
in the desktop app, follows your system's appearance instead.

A live frame nobody has on screen pauses a few seconds later, and its page keeps
its state. Scroll back to it and it shows its last picture at once, then picks
up live where it left off. A workspace keeps six frames' browsers open. Past
that, the frame nobody has looked at for longest closes its browser, and the
next time someone looks at it, it reopens at the page it was on, still signed
in and with its saved settings, but anything the page only held in memory,
like a half-filled form, starts over.

The desktop app has no **Go live**: there, every frame is a preview running
on your Mac.

## The agent driving a frame

A Workspace chat's agent can use a frame: click, type, press keys, scroll,
pick options, drag and hover, like you would. It reads the page's buttons, links and
fields to find what to act on, and looks at the frame after each step to
check it worked. Ask it to show you what it built, or to get a frame into a
state for you.

How it drives depends on how you ask:

- **"Show me"** plays like a demo. The agent brings the frame into view for you,
  and a cursor labelled Agent glides to each button or field and pauses before
  it clicks, so you can follow along. Text goes in a character at a time.
- **"Get it into that state"** jumps straight to the end. There's no cursor,
  and your view of the canvas doesn't move.

Each step shows up in the chat as a short line, like **Click** `Save`,
**Hover** `Info` or **Type** `ada@example.com`, so you can see where it went if something goes
wrong. When no frame shows what it needs, or you're using the one there,
the agent opens a new frame beside its workspace's other frames instead of taking
yours over.

- **Asking is the go-ahead.** Asking the agent in the chat lets it drive, even
  while you're interacting with the frame, so there's no second prompt.
- **You can take over at any moment.** Click the driver button (or
  double-click the frame) and the agent stops at once. It tells you where it got
  to and asks before it carries on; when you leave Interact, the frame is
  the agent's again.
- **It hands the frame back.** When it's done, or after a minute without a
  step, the frame stops showing the agent as its driver.

### On a shared canvas

On hosted Screenplay, the agent drives the frame's one live browser, and the
frame is live while it has control, so everyone on the live frame watches each
step as it happens. Everyone else sees **Agent has control** on their copy's
title line. Anyone
can take the frame from the agent; between people, the usual
[asking for control](#asking-for-control) applies. The agent can drive a frame
nobody is looking at, too: it keeps running while the agent works on it.
When you ask it to show you something, everyone watching sees its cursor, but
only your view moves to the frame.

The agent's clicks and keys reach the shared browser as real input, the same
as yours: focus, typing, <kbd>Tab</kbd> and hover styles all work, and native
dropdowns and date pickers open as they would for you. The one thing it can't
do is choose a file: when a step needs one, it asks you to pick it yourself.

### In the desktop app

- **It drives your own frame.** The steps happen in the frame on your canvas,
  and nothing is sent anywhere else.
- **Screenplay has to be open.** The agent drives only while the canvas is
  open in the desktop app. The window can be in the background while it works.
  With the canvas closed, the agent tells you so in the chat instead.

The agent's clicks and keys are simulated inside the page, so they do what the
page's own code listens for but not what the browser does for a real gesture.
On the Mac it can't:

- open the file picker, so it asks you to choose files yourself;
- copy or paste with the clipboard (a **Copy** button doesn't copy);
- type into rich-text editors, or move the keyboard focus (including with
  <kbd>Tab</kbd>), so anything that reacts to focus won't;
- open a native dropdown, date or colour picker, though it can still set the
  value.

It can hover: tooltips, hover cards and menus that open on hover do, and the
page's hover styles show, until its next step moves the pointer on. Hover
styles from a stylesheet on another site (a font or icon CDN, say) don't show,
and moving your own mouse over the frame hands hover back to you.

When a step needs one of these, the agent says which and asks you to do it in
the frame. Tell it in the chat when you're done, and it carries on from there.

The agent drives [mockups](/guides/mockups#the-agent-driving-a-mockup) the same
way,
in the browser too.

## Sizes

**More → Device size** sets exact device dimensions:

/>

| Group   | Presets                                                                                                                                                 |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Desktop | 4K (3840×2160), 1920×1080, MacBook Pro 16″ (1728×1117), MacBook Pro 14″ (1512×982), Laptop 1440×900, Laptop 1280×800                                    |
| Tablet  | iPad Pro 13″, iPad Pro 11″, iPad Air 13″, iPad Air 11″, iPad mini, Galaxy Tab S10 Ultra                                                                 |
| Mobile  | iPhone 17 Pro Max, iPhone 17 Pro, iPhone 17, iPhone Air, iPhone SE, Pixel 9 Pro XL, Pixel 9 Pro, Galaxy S25 Ultra, Galaxy S25, Galaxy Z Fold (unfolded) |

You can also drag a corner handle. While resizing, the frame **snaps** to
nearby device sizes, which are outlined as you get close. Hold <kbd>⌘</kbd>
to resize freely. **Fit to content** resizes the frame to the page's full
document size, which is handy for capturing a whole long page.

A repository's **Default frame size** decides what new frames open at.

## Knobs

If your app declares [knobs](/building/knobs), the **Knobs** button opens live
controls: sliders, switches, text fields, selects, and color pickers. Changes
apply instantly and sync to everyone viewing the canvas. A dot on the button
means values differ from their defaults, and **Reset** in its header clears
them.

<Screenshot
  name="knobs-popover"
  alt="The Knobs popover with Accent color, Corner radius, Headline, Show customer logos and Hero layout"
/>

With no knobs declared, the popover explains what knobs are and offers **Ask
the agent to add a knob**, which opens the workspace's chat with a prompt
filled in.

## Shared state

When your app shares state through
[`@screenplay.space/state`](/building/shared-state), a small `{}` appears on
the route in the selected frame's address bar. Hover it to see the current JSON. The state is kept with the
frame and synced to everyone.

## Preview states

While there's no live page, a frame shows where its workspace is:

- **No workspace** until you pick one for the frame.
- **Setting up the workspace**, then **Starting dev server**, while the workspace starts.
- **Workspace failed to start** if setup failed, and **Dev server not
  responding** if the server doesn't answer in time. Both offer **Retry** and
  **Open logs**.
- **Workspace stopped** when its sandbox is stopped. Click **Start**.

<Callout type="info">
  A preview that never loads on desktop usually means the dev server isn't
  listening on the port Screenplay assigned. See [Dev server &
  ports](/building/dev-server).
</Callout>
