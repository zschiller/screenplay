# Agent chat

The agent panel on the right (<kbd>⌘</kbd> <kbd>I</kbd>) is where you work
with the agent. With nothing selected it shows the canvas's
[Coordinator](#the-coordinator). Pick a workspace or a document and it chats
with that instead. In a workspace chat, everything the agent does happens
inside that workspace's sandbox.

## The Coordinator

The **Coordinator** is one chat for the whole canvas. It's where the panel
opens, and every canvas has exactly one, shared by everyone on it. It can see
every workspace (its title, status, changed lines and pull request), every
frame and document, and your terminal tabs, so you can ask things like
"What's on this canvas?" or "Which workspaces have a PR?" without opening
each one. It reads documents too, including ones you @ mention.

It can also look inside a workspace: what its agent was last asked, a summary
of what it did and its last reply (or the whole chat when it needs it), the
workspace's changes and its files. And it can look at a frame, taking a
screenshot of the live preview, or using the last saved one when the preview
isn't running. So you can ask "What did the sign-in workspace change, and how
does it look?"

<Screenshot
  name="coordinator"
  alt="The Coordinator chat, the panel's home when no workspace is selected"
/>

The Coordinator can also arrange the canvas. Ask it to add frames for a
workspace's routes, add a document, move or rename frames, groups and
documents, gather frames into a group, merge groups, or remove frames and
documents. It does these right away, without asking first. Removing a frame
never removes its workspace.

To take a change back, ask it: "undo that". It keeps what each of its replies
changed, so a frame or document it removed comes back exactly as it was, and
you can undo an undo the same way. Your own ⌘Z still undoes only your own
edits, never the Coordinator's.

The Coordinator never works inside a sandbox and never edits a workspace's
files. When you ask for work in a workspace, it sends that workspace's agent a
message, and the agent does the work. When no workspace fits, it can start new
ones, after you approve its plan.

### Messages to workspaces

Each workspace the Coordinator messaged shows up in its reply as a row with the
workspace's title, its changed lines and its state: **Starting** while its
sandbox comes up, **Working** while the
agent runs, **Needs you** when a plan waits for your approval, **Done**, or
**Failed**. The row updates as the workspace works. Click it to open that
workspace on the chat the message went to.

In the workspace's chat, the message shows as one line, **Received a message
from the Coordinator**. Click it to read what was asked. The chat is still
yours: type in it at any time to take over.

The Coordinator won't message a workspace whose agent is already working,
whose sandbox isn't running, or whose plan is waiting on you. It tells you
instead, and only you approve plans.

### Starting workspaces

When an ask needs work no workspace covers, the Coordinator proposes new
workspaces as a plan: one row per workspace with its title, its repository and
a one-line brief. Nothing is created until you click **Approve**. Click
**Request changes**, or just reply, to have it revise the list.

Once you approve, each workspace starts its sandbox, and its agent begins on
the Coordinator's first message as soon as the sandbox is running. The new
workspaces show up as rows in the Coordinator's reply, **Starting** at first.
They belong to whoever asked for them. If one fails to start, the others carry
on: its row shows **Failed**, the Coordinator tells you, and **Retry** on the
workspace brings it up and sends that first message then.

The Coordinator can also stop a workspace's running turn, which happens right
away. The workspace's chat keeps everything so far.

### Pull requests and removing workspaces

Ask the Coordinator to open a workspace's pull request or to remove a
workspace, and it asks you first with a card in its chat. Nothing happens until
you click **Open PR** or **Remove**; **Cancel** drops it, and the Coordinator
is told you said no.

The pull request goes from the workspace's git branch into the repository's
default branch, with its title and description taken from the branch's
commits, as the workspace chat's **Create PR** button does. It's opened with the
GitHub account of whoever owns the workspace, even when someone else asked or
the Coordinator followed up on its own.

Removing a workspace works like **Delete** in the sidebar: its chats and
frames go and its sandbox is torn down. The git branch and any pull request
stay on GitHub.

When the Coordinator runs on a desktop harness (Claude Code or Codex), it can't
show you a plan or a confirm card yet, so it can't start workspaces, open pull
requests or remove workspaces there.

### Trying something several ways

Ask the Coordinator to try one thing several ways, like "try the sign-in page
three ways", and it plans one workspace per variant, all from the same
repository and branch. Each row's brief says how that variant differs. Name
the directions yourself or let the Coordinator pick them; with no number, it
proposes three. Once you approve, the variants' frames sit side by side in one
group, so you can compare them on the canvas. When every variant has
finished, the Coordinator sums them up in one reply and leaves the pick to you.

### When a workspace finishes

The Coordinator hears from every workspace on the canvas, including ones you
started yourself. Each time a workspace's agent finishes, fails, is stopped or
stops to wait for plan approval, the Coordinator reads what happened.

It stays quiet unless there's something you need to know: a result, a
blocker, or a decision only you can make. When a workspace is waiting for you
to approve its plan, it tells you which one, with a link that opens it. You
approve the plan in the workspace; the Coordinator can't.

### Canvas memory

Each canvas keeps a shared **memory**: preferences, decisions and facts about
its repositories, like "Use pnpm, never npm." Every chat on the canvas reads
it, the Coordinator's and each workspace's and document's alike, so no chat has
to ask the same thing twice. On the desktop app, a chat that runs through an
external harness gets memory when the chat starts.

The Coordinator saves to memory when you tell it something worth keeping or
ask it to remember something, and it edits or removes entries when you ask.
Workspace agents read memory but never write it.

To read or change memory yourself, open **Canvas settings** from the **…**
next to the canvas name and choose **Memory**. **Edit** changes an entry,
**…** › **Delete** removes it, and **Add memory** adds one. Everyone on a
shared canvas sees the same entries.

## Choosing a target

Click a workspace in the sidebar to open its chat. The header then reads
**Coordinator / _workspace_**: click **Coordinator** to go back. After it
is the current **target**, a workspace with its status icon or a document.
Click it to switch to any running workspace (**Workspaces**, each with its
status icon and pull request) or document (**Documents**). When you switch back
to a target, the panel reopens the chat you last used there.

The header also shows the workspace's **+/−** diff and a **Create PR** button
(see [Pull requests](/guides/workspaces#pull-requests)).

## Tabs

Each target has its own set of tabs:

- **Sandbox logs** (the first icon) streams the setup script and dev server
  output. It opens automatically while a workspace is starting.
- **Chat tabs**, as many as you like. New chats are named from their first
  message. A spinner means the agent is working; a magenta dot means there's a
  reply you haven't seen.
- **Terminal tabs**: see [Terminal tabs](/guides/terminals).

<Screenshot
  name="new-tab-menu"
  alt="The new-tab menu: New chat and New terminal"
/>

**+** opens a new tab of whichever kind you used last. The caret next to it
lets you choose. Double-click a tab to rename it, drag to reorder, and hover
to close. Closed chats aren't lost: reopen them from the **Chat history**
menu at the end of the strip, which lists them with their date and first
message, and where you can delete them for good. Closing a target's last tab opens a fresh
one. If a target ends up with no open tabs anyway (you deleted its last chat
from the history, say), the panel says **No open chats** with a **New chat**
button.

## The composer

Type a message and press <kbd>↵</kbd> to send. <kbd>⇧</kbd> <kbd>↵</kbd> adds a
new line. While the agent is working, the send button becomes **Stop**.
Stopping ends the turn with a **Stopped** line in the chat, which looks the
same after a reload. If you type while it works, the button becomes **Queue
message**, and the message sends when the agent finishes. Each chat keeps its
own draft, and a message that couldn't be sent stays in the chat with **Retry**
and **Edit**.

### Choosing a model

The model menu sits at the bottom left of the composer. New chats start with
the default agent and model from [Settings](/guides/settings#coding-agents-desktop).
Changing the model in a chat changes only that chat, and the menu shows
**· not default** when it differs. You can switch at any point in a chat: the
new model answers from your next message on, with the whole conversation so far.
Switching to another coding CLI's model starts that CLI with the conversation
replayed to it.

- **Desktop** lists your installed coding CLIs with their models, for example
  **Claude Code**: Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 4.5, and **Codex**:
  GPT-6 Astra, GPT-6 Luna, GPT-5.5.
- **Hosted** lists the models of every provider the operator configured
  (Anthropic, OpenAI, Google, Vercel AI Gateway, OpenAI-compatible).

### Mentioning documents

Type <kbd>@</kbd> to mention a [document](/guides/documents). The agent is
told which documents you mentioned and reads their current contents, so
there's no need to paste anything.

### Loading a skill

In workspace chats, type <kbd>/</kbd> to insert a [skill](/building/skills):
a packaged set of instructions the agent loads before starting. Skills tagged
**App** ship with Screenplay. Skills tagged **Repo** come from the
repository's `.claude/skills/` folder.

### Targeting an element

Instead of describing a button, point at it. Click the **crosshair** (or
press <kbd>⌘</kbd> <kbd>E</kbd>), then click any element in one of this
workspace's frames. A token like `⌖ a` is inserted where your cursor was, and
the agent receives the element's CSS selector, route, and frame. Hover the
token to highlight the element on the canvas. <kbd>Esc</kbd> cancels picking.

## Plan mode

Turn on **Plan** in the composer when you want to approve the approach before
any code changes. The agent investigates, then presents a **Plan** card
instead of editing. Plan mode is for workspace chats; the composer in a
document chat has no **Plan** toggle.

<Screenshot
  name="plan-card"
  alt="An approved plan card for adding an FAQ, followed by the agent implementing it"
/>

- **Approve** tells the agent to go ahead.
- **Request changes** quotes the plan in the composer so you can add your
  feedback. Any message sent while a plan is pending counts as feedback, so
  you can also just reply, and the agent revises the plan.

## Following the work

Agent replies stream in as they're written. Each tool call is a compact row
you can expand for details:

| Row                                | Meaning                                      |
| ---------------------------------- | -------------------------------------------- |
| **Read** _n_ lines `path`          | Read a file                                  |
| **Edit** / **Write** `path`        | Changed a file (expand to see the diff)      |
| **Run command** `…`                | Ran a shell command in the sandbox           |
| **List files**, **Grep**, **Glob** | Searched the code                            |
| **Read skill** `name`              | Loaded a skill's instructions                |
| **Read document**                  | Read a document on the canvas                |
| **Create PR**                      | Opened a pull request (shown as a link card) |
| **Submit plan**                    | Presented a plan for approval                |

Failed calls are marked in red and always show the error, or say that none
was reported. Once a turn finishes, its tool calls fold behind one summary
line of what the agent read, edited and ran; expand it to see them again. Secrets such as GitHub tokens are redacted from tool output.

A few defaults are worth knowing:

- **The agent commits and pushes after every change.** Commits are made under
  your identity, which matters on shared canvases.
- **The workspace preview updates on its own.** The dev server hot-reloads as
  files change.
- **Chats are shared.** On a shared canvas everyone sees every chat live,
  including history from before they joined.

## Workspace, branch and chat naming

A new workspace starts with a random branch name. The first message in its
first chat titles the workspace ("Hero Gradient & Trust Line"), renames the
branch to match (for example `hero-gradient-trust-line`) and names the chat
the same. If the branch name is already taken on the remote, a numeric suffix
is added. Later chats get their own names but leave the workspace's title and
branch alone. See [Titles](/guides/workspaces#titles).

<Callout type="info">
  **"No coding agent detected"** on desktop means no supported CLI is installed.
  Install one from **Settings → Coding agents**; it shows up without a restart.
</Callout>
