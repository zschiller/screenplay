# Workspace chats

The agent panel on the right (<kbd>⌘</kbd> <kbd>I</kbd>) is where you work
with the agent. With nothing selected it shows the canvas's
[Coordinator](/guides/coordinator). Pick a workspace and it chats with that
workspace's agent instead, and everything the agent does happens inside that
workspace's sandbox.

The Coordinator uses the same composer, with less in it. It is one chat with
no tabs, and has no **Plan** toggle, <kbd>/</kbd> skills menu or crosshair.

Every workspace has exactly one chat, from the moment it starts, and that chat
is the only one that changes the workspace's code. More work in parallel means
more workspaces: each is its own branch, sandbox, dev server and chat. A
workspace's chat can read other workspaces' code and frames, but never changes
them. It can also [write documents](/guides/documents#documents-a-chat-writes)
on the canvas, and edits the ones it wrote.

## Choosing a target

The **Workspaces** button at the far right of the Coordinator's header opens the
list of every chat on the canvas: the **Coordinator**, each workspace with its
status icon and pull request (see
[The Workspaces menu](/guides/workspaces#the-workspaces-menu)). Pick one to
open its chat. When you switch back to a target, the panel reopens the chat
you last used there.

In a workspace the header reads **Coordinator / _workspace_**: click
**Coordinator** to go back. The workspace's name with its status icon only
says where you are; hover it for the workspace's
[hover card](/guides/workspaces#the-hover-card). To its right are the
workspace's **+/−** diff and a **Create PR** button (see
[Pull requests](/guides/workspaces#pull-requests)).

## Tabs

Each workspace has its own set of tabs:

- **Sandbox logs** (the first icon) streams the setup script and dev server
  output. It opens automatically while a workspace is starting, and stays put
  at the left when the other tabs overflow and scroll.
- **The chat tab**: the workspace's one chat, named from its first message. A
  spinner means the agent is working; a pink dot means there's a reply you
  haven't seen. It has no close button.
- **Terminal tabs**: see [Terminal tabs](/guides/terminals).

**+** opens a new terminal tab; there's no second chat to open. Double-click a
tab to rename it, drag to reorder, and hover a terminal to close it.

A canvas from before workspaces had one chat can hold several chats on one
workspace. The newest is the workspace's chat. The others are **earlier
chats**: you can still open and read them, and close them, but they can't
send. In place of the composer they point you to the workspace's chat. Closed
earlier chats stay in the **Chat history** menu at the end of the strip, with
their date and first message, where you can reopen them or delete them for
good.

## The composer

Type a message and press <kbd>↵</kbd> to send. <kbd>⇧</kbd> <kbd>↵</kbd> adds a
new line. While the agent is working, the send button becomes **Stop**.
Stopping ends the turn with a **Stopped** line in the chat, which looks the
same after a reload. Each chat keeps its own draft, and a message that
couldn't be sent stays in the chat with **Retry** and **Edit**. Pasting an
image isn't supported yet: describe it, or paste a link to it.

### Sending while the agent works

You don't have to wait for the agent to finish, or stop it, to correct it.
Type while it works and press **Send**: the message shows at the end of the
chat, dimmed and marked **Waiting for the agent**, for everyone on the canvas.
The agent reads it as soon as it finishes the step it's on (the model reply or
tool call in progress), and the message moves to that point in the chat. The
turn carries on with it; nothing is cancelled. Several messages sent before the
agent gets to them reach it together, in the order you sent them.

If the turn ends before the agent reads a message, the message starts the next
turn straight away. If you press **Stop** instead, messages still waiting go
back into your composer, so you can decide whether to send them.

The built-in agent works this way in every chat, including the Coordinator,
and so do chats running Claude Code or Codex on desktop: each reads the message
at the same point it would if you typed it into its own terminal. Chats
running OpenCode don't yet: there the button reads **Queue message**,
and the message waits in a **Queued** row above the composer, where you can
**Edit** or remove it, and sends when the agent finishes.

### Choosing a model

The model menu sits at the bottom left of the composer and names the current
model; its list groups models under their coding CLI. New chats start with
the default agent and model from [Settings](/guides/settings#coding-agents-desktop).
Changing the model in a chat changes only that chat, and the menu shows
**· not default** when it differs. You can switch at any point in a chat: the
new model answers from your next message on, with the whole conversation so far.
Switching to another coding CLI's model starts that CLI with the conversation
replayed to it.

- **Desktop** lists your installed coding CLIs with their models, for example
  **Claude Code**: Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 4.5, and **Codex**:
  GPT-6 Astra, GPT-6 Luna, GPT-5.5.
- **Hosted** lists the models of every provider the operator configured
  (Anthropic, OpenAI, Google, Vercel AI Gateway, OpenAI-compatible).

### Mentioning documents

Type <kbd>@</kbd> to mention a [document](/guides/documents). The agent is
told which documents you mentioned and reads their current contents, so
there's no need to paste anything.

### Loading a skill

In workspace chats, type <kbd>/</kbd> to insert a [skill](/building/skills):
a packaged set of instructions the agent loads before starting. Skills tagged
**App** ship with Screenplay. Skills tagged **Repo** come from the
repository's `.claude/skills/` folder.

### Targeting an element

Instead of describing a button, point at it. Click the **crosshair** (or
press <kbd>⌘</kbd> <kbd>E</kbd>), then click any element in one of this
workspace's frames. A token like `⌖ a` is inserted where your cursor was, and
the agent receives the element's CSS selector, route, and frame. Hover the
token to highlight the element on the canvas. <kbd>Esc</kbd> cancels picking.

## Plan mode

Turn on **Plan** in the composer when you want to approve the approach before
any code changes. The agent investigates, then presents a **Plan** card
instead of editing. Plan mode is for workspace chats; the Coordinator has no
**Plan** toggle.

<Screenshot
  name="plan-card"
  alt="An approved plan card for adding an FAQ, followed by the agent implementing it"
/>

- **Approve** tells the agent to go ahead.
- **Request changes** quotes the plan in the composer so you can add your
  feedback. Any message sent while a plan is pending counts as feedback, so
  you can also just reply, and the agent revises the plan.

## Questions

When the agent reaches a fork only you can decide, it can ask you with a
question instead of guessing: one sentence, with two to four options to pick
from, and the one it would pick marked **Recommended**. Pick an option to send
it as your reply; the agent carries on from there. To answer
something else, just type it in the composer.

Once answered, the question keeps the option you chose selected and can't be
answered again. Workspace chats and the [Coordinator](/guides/coordinator)
can both ask questions this way, in the browser and on desktop, including
chats running on Claude Code, Codex or OpenCode.

## Following the work

Agent replies stream in as they're written. Each tool call is a compact row
you can expand for details:

| Row                                | Meaning                                      |
| ---------------------------------- | -------------------------------------------- |
| **Read** _n_ lines `path`          | Read a file                                  |
| **Edit** / **Write** `path`        | Changed a file (expand to see the diff)      |
| **Run command** `command`          | Ran a shell command in the sandbox           |
| **List files**, **Grep**, **Glob** | Searched the code                            |
| **Read skill** `name`              | Loaded a skill's instructions                |
| **Read dev server logs**           | Read the dev server's recent output          |
| **Restart dev server**             | Restarted the workspace's dev server         |
| **View frame**                     | Took a screenshot of a frame                 |
| **Read frame HTML**                | Read the page in a frame as HTML             |
| **Read document**                  | Read a document on the canvas                |
| **Create PR**                      | Opened a pull request (shown as a link card) |
| **Submit plan**                    | Presented a plan for approval                |
| A question with options            | Asked you to pick an option                  |

Failed calls are marked in red and always show the error, or say that none
was reported. Once a turn finishes, its tool calls fold behind one summary
line of what the agent read, edited and ran; expand it to see them again. Secrets such as GitHub tokens are redacted from tool output.

A few defaults are worth knowing:

- **The agent commits and pushes after every change.** Commits are made under
  your identity, which matters on shared canvases.
- **The workspace preview updates on its own.** The dev server hot-reloads as
  files change. The agent can read the dev server's output (the same as the
  **Sandbox logs** tab) to debug a broken preview, and restart the dev server
  when a change needs it.
- **The agent can see the frames.** It can take a screenshot of a frame, or
  read the page in it as HTML with the styles included, for example to start a
  mockup from how the app looks now. It reads its own workspace's frame unless
  it names another one; any frame on the canvas can be read, never changed.
  Workspace chats running on Claude Code, Codex or OpenCode on desktop get
  these tools and the dev server ones too.
- **Chats are shared.** On a shared canvas everyone sees every chat live,
  including history from before they joined.

## Chat naming

A workspace's chat is named from its first message. That message usually
titles the workspace and names its branch too, and then the chat takes the
workspace's title; see [Titles](/guides/workspaces#titles) for when it does.

<Callout type="info">
  **"No coding agent found"** on desktop means no supported CLI is installed.
  Install one from **Settings → Coding agents** (the composer links there); it
  shows up without a restart.
</Callout>

## When something fails

A failed step in a chat says what failed in one line. Where the chat can try
again (approving a plan, stopping a run, or a turn you started that stopped
responding) the line has **Retry**, and **Copy error** copies the original
error for a bug report. Retrying a turn runs it again on the message you
already sent, so the message isn't posted a second time. A chat whose history or model list didn't load says so
with **Retry**, rather than looking empty or telling you to install an agent
you already have.
