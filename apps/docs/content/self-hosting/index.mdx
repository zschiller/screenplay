# Self-hosting

There are three ways to run Screenplay:

| | Who writes | Where it runs | Needs |
| --- | --- | --- | --- |
| **Hosted** | Everyone who signs in with GitHub | A Next.js deployment, a cloud sandbox per chat | The services below |
| **Desktop app** | You | Your Mac | Nothing: [download it](/guides/quickstart) |
| **[Headless](/self-hosting/headless)** | You, the host, over an SSH tunnel | A Linux machine you control, run from a clone | Node, git, a coding CLI and `gh` on that machine |

The desktop app and Headless swap every backend below for a local one. The
rest of this page covers deploying Hosted: a multi-user Next.js app where
people sign in with GitHub, share canvases, and each chat runs in its own cloud
sandbox VM.

## How it fits together

<ArchitectureDiagram />

Every backend sits behind a small interface in `apps/app/lib/`, so each one is
swappable. The defaults are what the reference deployment uses:

| Service | Used for | Default | Alternatives |
| --- | --- | --- | --- |
| **Hosting** | Running the Next.js app | [Vercel](https://vercel.com) | Anything that runs Next.js |
| **GitHub OAuth app** | Sign-in, plus `repo` scope to clone and push for users | [GitHub](https://github.com/settings/developers) | — |
| **Postgres** | Users, sessions, canvases, members, comments, agent history, encrypted settings | [Neon](https://neon.tech) (serverless HTTP driver) | Any Postgres; [swap the driver](/self-hosting/database#using-a-different-postgres-driver) |
| **Yjs host** | Realtime sync of each canvas document, agent streams, and presence | [Liveblocks](https://liveblocks.io) | Hocuspocus, y-websocket, … ([how](/self-hosting/configuration/yjs-host)) |
| **Sandbox provider** | One Linux VM per chat | [Vercel Sandbox](https://vercel.com/docs/vercel-sandbox) | E2B, Modal, … ([how](/self-hosting/configuration/sandbox-provider)) |
| **Model provider** | The agent. At least one is required. | Anthropic | OpenAI, Google, Vercel AI Gateway, any OpenAI-compatible API ([how](/self-hosting/configuration/model-providers)) |
| **Blob store** | Canvas thumbnails | [Vercel Blob](https://vercel.com/docs/vercel-blob) | S3, R2, GCS, … ([how](/self-hosting/configuration/blob-store)) |

## Setup order

<Steps>

### Create the accounts

Sign up for each service in the table, or pick alternatives.

### Create a GitHub OAuth app

One app covers production and every preview deploy. See
[GitHub OAuth](/self-hosting/github-oauth).

### Provision Postgres

Any Postgres works, and migrations run automatically on deploy. See
[Database](/self-hosting/database).

### Collect your environment variables

Every variable is documented in
[Environment variables](/self-hosting/environment-variables).

### Deploy

See [Deploying to Vercel](/self-hosting/deploying-to-vercel), including
which variables go in which Vercel scope.

### Optional: tune the configuration

Install [coding CLIs](/self-hosting/configuration/byo-harnesses) in sandboxes, [serve under a path prefix](/self-hosting/configuration/mount-path),
or swap any backend listed under **Configuration**.

</Steps>

## Trust model

The hosted build assumes a **single trusted operator**, or a fully trusted
team. The operator’s model API keys are shared by everyone and aren’t metered
per user. Coding CLIs in sandboxes never see those keys, because the
sandbox’s egress firewall injects them on the way out. Terminal access is
gated by canvas membership. Read
[Terminal access](/self-hosting/environment-variables#terminal-access) before
choosing a strategy for a shared deployment.
