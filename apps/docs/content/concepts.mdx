# Core concepts

Screenplay has a small set of nested ideas. Once they click, the rest of the
UI follows.

## Canvas

A **canvas** is the container for one piece of work: a feature, a redesign,
an experiment. It's an infinite, zoomable surface with the sidebar on the left
and the agent panel on the right. Canvases live on the
[home screen](/guides/home), where you can file them into folders and pin
them. On the hosted app you can [share](/guides/collaboration) a canvas, and
everyone in it sees the same layout, previews, and agent activity in real
time. Its setup lives in **Canvas settings**, under the **…** next to its
name.

## Coordinator

The **Coordinator** is the canvas's own chat, and where the agent panel opens.
Every canvas has exactly one, shared by everyone on it. It sees the whole
canvas: each workspace's status, changes and pull request, and every frame and
document. It arranges the canvas for you, and when you ask for a change, a
document or a mockup it sends a message to the right workspace's agent, which
does the work. The Coordinator makes nothing itself. It can also start new workspaces, open a
workspace's pull request and remove a workspace, right away.
→ [The Coordinator](/guides/coordinator)

## Repository

A **repository** on a canvas is the code its workspaces run, together with the
settings Screenplay needs to run it: a setup script (for example
`npm install`), a run script that starts the dev server, and a few optional
extras. You add and edit them in Canvas settings. One canvas can hold several
repositories, for example a web app and its API. The same repository can also
appear twice with different settings, which suits monorepos. Your repositories
live in **Settings → Repositories**, ready to add to any canvas.
→ [Repositories](/guides/repositories)

## Workspace

A **workspace** is one git branch of a repository, running in its own isolated
**sandbox**:

- On the **desktop app**, a sandbox is a git worktree on your machine, and the
  dev server runs locally on a port assigned to that workspace.
- On the **hosted app**, a sandbox is a cloud VM with its own clone of the
  repository.

Each workspace has a title (the agent writes it from your first message), its
own dev server, and its own agent chat and terminals. The **Chats**
button at the top right of the agent panel lists every chat in one flat
list, like threads in a project: the Coordinator, then each workspace's chat
by its title. On a canvas with several repositories each row ends with its
repository's name.
Workspaces are cheap: create one for every idea you want to try and compare
them side by side.
→ [Workspaces](/guides/workspaces)

## Frame

A **frame** is a live preview on the canvas. It shows one route of one
workspace's dev server at a chosen device size. Frames are real browsers:
switch into **Interact** mode and you can click through the app.
→ [Frames](/guides/frames)

## Document

A **document** is a rich-text page on the canvas for specs, checklists, notes
and plans. Documents are edited collaboratively, and a workspace's chat can
write one for you and keep editing it.
→ [Documents](/guides/documents)

## Mockup

A **mockup** is a static page a workspace chat draws on the canvas to show a
design option. It needs no dev server, so it shows up at once, beside its
workspace's frames or in a group of its own. It shows the workspace of the chat
that made it, and only that chat can change it. → [Mockups](/guides/mockups)

## Group

A **group** is a row of frames, documents and mockups laid out left to right, so the
desktop and mobile versions of a page, or the steps of a flow, stay together.
Every frame, document and mockup lives in one. When all of a group's frames show the
same workspace, as the screens of one flow do, the group names it once;
otherwise each frame names its own.
→ [Groups](/guides/canvas#groups)

## Workspace agent

A **workspace agent** does the coding. Every workspace has exactly one chat,
and only that chat changes its code. When you (or the Coordinator) give it
work, it reads files, edits them, runs commands, and commits inside that
workspace's sandbox. It can read other workspaces' code, but never changes
it. Where the agent comes
from depends on how you run Screenplay:

- **Desktop**: the coding CLI installed on your machine (Claude Code or Codex),
  running on your own login.
- **Web app**: a built-in agent loop that uses the model providers the operator
  configured (Anthropic, OpenAI, Google, the Vercel AI Gateway, or any
  OpenAI-compatible endpoint).

Alongside chat, **terminal tabs** give you plain interactive shells in the
same sandbox. → [Workspace chats](/guides/agent),
[Terminal tabs](/guides/terminals)

## Memory

Each canvas keeps a shared **memory**: preferences, decisions and facts about
its repositories, like "Use pnpm, never npm." Every chat on the canvas reads
it, so no chat has to ask the same thing twice. The Coordinator saves to it
when you tell it something worth keeping, and you can edit it in Canvas
settings. → [Canvas memory](/guides/coordinator#canvas-memory)

## Names you'll see in the code

The UI labels are deliberately friendlier than the code's names. If you read
the source or the self-hosting docs:

| In the UI       | In the code        |
| --------------- | ------------------ |
| Canvas          | Room               |
| Repository      | Repo               |
| Coordinator     | Room Target        |
| Workspace       | Branch             |
| Frame           | Iframe Layer       |
| Group           | Iframe Layer Group |
| Document        | Markdown Layer     |
| Mockup          | Mockup Layer       |
| Workspace agent | Engine             |
