# Screenshots

The **screenshot harness** (`apps/app/screenshots/`) boots the local build
against a seeded world and photographs it. It serves two jobs: before/after
screenshots for design review, and the screenshots in these docs
([Docs screenshots](#docs-screenshots)).

Every design-polish ticket ships before/after screenshots on its PR, so design
can be reviewed in the pull request instead of by cloning the branch. The
harness is the scripted path to those images: one command boots the local build against a seeded fixture world, one
captures the named screens in light and dark, one records a short video of a
named interaction.

## The three commands

Run them from `apps/app`.

```bash
pnpm screenshots:browsers   # once per machine: download Chromium + ffmpeg
pnpm screenshots:boot       # seed a fresh world and serve it at :3947
pnpm screenshots:shots      # capture every named screen, light and dark
pnpm screenshots:video open-canvas   # record one named interaction (GIF + MP4)
```

`shots` and `video` boot the app themselves when nothing is serving the port,
and reuse a `boot` you already have open when there is — so the first is a
one-shot in a cold container and the second is a fast re-shoot while you
iterate. Whichever one started the server stops it again.

## The before/after workflow

Capture the base branch first, then your own, into two labels:

```bash
git switch main
pnpm --filter app screenshots:shots --label before

git switch my-polish-branch
pnpm --filter app screenshots:shots --label after
```

Both runs shoot the same named screens at the same size, so
`.screenshots/captures/before/` and `.screenshots/captures/after/` hold
matching filenames and any image-diff tool pairs them without configuration.
Attach the pairs that changed to the PR — not the whole set.

Both branches need the harness for this to work, which is true of anything
merged after it landed. Against an older base, capture "before" from a
worktree instead:

```bash
git worktree add ../screenplay-before <old-base>
cd ../screenplay-before && pnpm install
pnpm --filter app screenshots:shots --label before \
  --out ../screenplay/apps/app/.screenshots/captures
```

### Narrowing a run

```bash
pnpm screenshots:shots --list                    # the named screens
pnpm screenshots:shots --screens canvas,settings # just these
pnpm screenshots:shots --themes dark             # just one theme
pnpm screenshots:shots --fresh                   # re-seed a clean world first
```

`--fresh` needs the database to itself, so stop a running `boot` before using
it.

### Recording an interaction

A still can't review motion — an entrance animation, a drag, a panel that
slides. `video` records one named flow to
`.screenshots/captures/videos/<name>.<theme>.gif` and `.mp4`:

```bash
pnpm screenshots:video --list
pnpm screenshots:video canvas-zoom --theme dark
```

Embed the GIF in the PR description as an image (`![](…/canvas-zoom.dark.gif)`):
it plays inline. Link the MP4 under it for full quality; it plays in QuickTime,
Safari and Chrome. Don't post the `.webm` Playwright records: GitHub downloads
it instead of playing it, and a Mac can't open it. A busy recording steps down
in size and frame rate until the GIF is under 10 MB, so the PR stays quick to
open.

The encoder uses `ffmpeg` from your `PATH` when it can write GIF and H.264, and
otherwise installs a static build once into `.screenshots/tools/`
(`SCREENSHOTS_FFMPEG` points it at a specific binary). A recording
made outside the harness (a one-off Playwright script) converts the same way:

```bash
pnpm screenshots:review-video path/to/recording.webm
```

Name the flow in the PR ("recorded `open-canvas`") so a reviewer can re-record
the same one on their branch and compare like for like.

## Adding a screen

`apps/app/screenshots/screens.ts` is the named screen list, and adding to it is
a few lines. Light and dark, the viewport, settling, and the output filename are
the runner's job:

```ts
{
  name: "canvas-narrow",
  description: "The Canvas at a narrow window, where the panels compete for width.",
  path: `/${ids.rooms.checkout}`,
  viewport: { width: 1024, height: 768 },
}
```

A screen that needs a panel open or a tab selected adds `cookies` (preferred —
the screen paints correct rather than being clicked correct) or a `prepare`
step. A `prepare` that can't find its target warns and the screen is captured
without it, rather than sinking the run.

A surface whose content streams in over the network — the terminal's
WebSocket, the sandbox logs — adds `beforeNavigate` stubs, installed before the first
navigation, since the fixture world has no running sandbox to answer.
`screenshots/fixtures/streams.ts` has the terminal and logs stubs the
`terminal`, `logs-reconnecting` and `logs-error` screens use.

A failure state is simulated rather than staged. `failServerActions` (in
`screens.ts`) answers every server action with a 500, from `beforeNavigate` to
fail a page's loads or from `prepare` to fail only the mutation it then drives.
A failure the browser can't cause, such as the home layout's server-side load,
is a **fixture fault**: a cookie `apps/app/lib/fixture-faults.ts` honours only
in the fixture world (`fixtureFault("home-load")`).

Interactions live next door in `interactions.ts`, same shape.

## The fixture world

`apps/app/screenshots/fixtures/world.ts` describes everything the harness seeds
— Canvases (including an empty one) filed into Folders, a Repository with a
Workspace in each status, iframe and Document Layers, a chat with tool calls, a
pending plan, terminal tabs, pins, and saved Repository presets. It is data only;
`fixtures/seed.ts` is the single writer that turns it into PGlite rows, Y.Docs,
and blobs.

Every id is a stable literal and every timestamp is derived from one instant, so
two runs produce the same URLs and the same relative dates — which is what makes
a before/after pair diffable at all. `world.test.ts` holds the world to its own
rules (every Layer in exactly one Group, every Pin pointing at something real,
every Workspace status covered), so extending it is safe.

Need one more state on screen? Add it to the literal. That's the intended way to
use this.

### Frames have content

Each fixture Workspace points at a small **fixture preview server** the harness
runs beside the app, which serves a flat wireframe per route and inlines the
real Sandbox Bridge. So frames load, report ready, and drop the "Waiting for dev
server…" overlay exactly as a real Workspace's would — without cloning a repository or
running `pnpm install` per Workspace. The pages are deliberately not mock
product screens.

### Fixture mode

The harness runs the app with `NEXT_PUBLIC_SCREENPLAY_FIXTURE_WORLD=1`
(`apps/app/lib/fixture-world.ts`), which tells it that the world on disk is
already what it should be, so it doesn't go looking at the host: the first-run
setup gate opens without probing for a coding CLI, Sandbox Reconnect doesn't
reconcile Workspaces that have no sandboxes behind them, and opening a Canvas to
photograph it doesn't restamp it as just-edited. It is `and`-ed with
`isLocalBuild`, so the hosted app can never enter it.

## Docs screenshots

The same harness produces the screenshots in these docs, from a second world
built to tell one story: a team building "Northwind", a small marketing site.
It lives in `apps/app/screenshots/docs/`:

| Path            | What it owns                                                                                                                                 |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `world.ts`      | The **docs world**: the Northwind Canvas and three more, filed into Folders, with Workspaces, frames, a document, and chat transcripts.      |
| `demo-site.ts`  | Builds the demo site in `northwind/` once per Workspace, with that Workspace's edits applied, and serves each from its own origin.           |
| `thumbnails.ts` | Photographs those previews for the home grid's cards.                                                                                      |
| `screens.ts`    | The **docs screen list**: one entry per `<Screenshot name="…">` in the docs.                                                                 |
| `frame.ts`      | Frames each capture as a desktop window, or as a magnified detail centred on its focus, into `apps/docs/public/screenshots/`.               |

Unlike the design-review world, the frames here are a real React site built
against this repository's `@screenplay.space/knobs` and `@screenplay.space/state`, so
knobs, shared state, element targeting and play mode all work. The edit each
Workspace's agent made is defined once, in `demo-site.ts`: it is applied to that
Workspace's build and appears as the diff in its chat.

Regenerate everything with:

```bash
pnpm --filter docs screenshots   # same as: pnpm --filter app screenshots:docs
```

It seeds the docs world, captures every docs screen in light and dark, and
writes the framed WebP files. Review the changed images before committing them.

While you work on a screen, keep the world open and re-shoot only that screen:

```bash
pnpm --filter app screenshots:docs --boot                       # terminal 1
pnpm --filter app screenshots:docs --screens ws-menu --themes light   # terminal 2
```

A run that finds `--boot` serving shoots against it instead of re-seeding.
`--list` prints the screen list, `--no-frame` stops after capturing, and
`--frame-only` re-frames the last capture.

### Kept up to date automatically

The **Docs screenshots** workflow (`.github/workflows/docs-screenshots.yml`)
reruns this on every push to `main` that touches the app, the UI packages, or
the docs. When any image changes, it opens a `docs: refresh screenshots` pull
request (or updates the open one) for someone to look over and merge. It runs
with `--strict`, so a screen whose steps fail stops the run instead of
proposing a wrong image; the raw captures are attached to the run.

Re-runs are stable, so the pull request only appears when the UI really
changed. The docs world is anchored to a fixed instant (`DOCS_NOW` in
`world.ts`), every capture freezes the browser clock just after it, and the
framing step keeps an existing image when the new render is visually the same.

### Adding a docs screenshot

1. Add an entry to `DOCS_SCREENS` in `screens.ts`. Its `name` is the one you
   pass to `<Screenshot name="…">`.
2. For a full-window shot, that's it. For a detail shot, give it a `focus`:
   selectors for what the image is about, such as `MENU`, `DIALOG` or
   `POPOVER`, or a function that measures it. After `prepare`, the visible
   matches are measured, and the framing step crops a detail centred on them,
   with room around them, as the bare UI: no window chrome, shadow or
   backdrop. A crop edge near the window's edge is pushed out to it, rather
   than slicing labels a few letters in. So when a UI change moves a menu,
   the next run still frames it whole and centred. A fixed `crop`
   (`[x, y, width, height]` in CSS px) stands in when nothing matches.
3. If the screen needs state the world doesn't have, add it to `world.ts`.
4. Run `pnpm --filter app screenshots:docs --screens <name>` and embed it.

## What the local build doesn't have

The local build excludes the entire multi-user surface (see
[Local (single-user) build](/self-hosting/configuration/local-build)), so these never appear
in a plain capture:

- **Comments** — threads, pins, replies, read state, the comment lists.
  (Reply in chat on document text _is_ kept.)
- **Cursors and presence** — with one local Yjs peer there is nobody else on the
  canvas; the follow toolbar is hidden.
- **Sharing and membership** — no `room_member`, no Share affordances, no
  collaborator lists.
- **Sign-in** — there is no login screen to shoot.

### The hosted capture

Add `--hosted` to any harness command to shoot the **hosted build** instead:

```bash
pnpm screenshots:shots --hosted --label after
```

It runs the same fixture world with the multi-user surface switched back on:
the hosted migrations into the same embedded Postgres, every Canvas shared with
a second fixture person, comment threads (including two written the way the
retired play-mode feed wrote them), and a signed-in session whose cookie the
capture browser carries, so there's no GitHub sign-in. Its state lives in
`.screenshots/hosted/` and it serves on port 3949, so it never collides with a
local run.

A screen with `hosted: true` in `screens.ts` is shot only by hosted runs, and a
hosted run shoots only those, so each set still diffs file-for-file. The
comment screens (`player-comments`, `canvas-comments-list`, …) live there.

Two more things vary by machine rather than by branch, so ignore them in a diff
(or leave those screens out of it):

- **Settings → Coding agents** reads the host live, so it shows whichever CLIs
  are installed where you ran the capture.
- **Thumbnail capture**: the harness seeds each Canvas's thumbnail itself, but a
  running app may re-capture frames with headless Chromium. It can't launch as
  root (so a container run logs a skip and keeps the seeded images) and the
  seeded and re-captured versions differ slightly.
