Round 1

The broad pass

Why it feels unresolved

Two things called “project”

In the app a Project is a repository with run scripts. Since #873 the Canvas chat works like a Claude project chat, which makes the canvas the real project.

Settings sit in the navigation

You set up a repository once and then mostly leave it alone. It still takes the top of the sidebar as the level every Workspace hangs under.

The branch is the name

A Workspace has no title, so its git branch labels it everywhere. Claude Projects names a thread by what it's about and keeps branches in the details.

Why settings are on the canvas

You guessed right. The canvas is what's shared, so a collaborator's new Workspace runs the same scripts without your private presets. The limit to design around is that one preview needs one running checkout.

Question 1

Where does a repository and its run settings live?

1A · today

A level in the canvas sidebar

A repo is a folder in the sidebar with its Workspaces inside.

  • Several repos per canvas are easy to see
  • Setup takes the top of the navigation
  • Called “Project”, like the canvas
1B

Canvas settings › Repositories

Out of the sidebar and into a settings page beside Memory (#874) and Members, like repositories in Claude project settings.

  • One word per level
  • Still shared on the canvas
  • Adding a repo is one step further away
1C

One repository per canvas

New canvas starts by choosing a repo. The canvas is about that repo. A second repo is an advanced setting.

  • Simplest model for the common case
  • No repo anywhere in the day-to-day UI
  • Web + API work becomes awkward
1D

Project above the canvas

On the home screen, a Project is a repo with its settings, and canvases live inside it, like Figma team projects hold files.

  • Set up once, reused by every canvas
  • Answers “why is config per canvas”
  • Replaces folders or competes with them
  • A canvas spanning two repos needs a home
1E

In the repository itself

A committed screenplay.json holds the scripts, like Conductor's config or a dev container. The canvas only links the repo.

  • Shared through git with anyone
  • Can seed any of 1A–1D
  • Needs a commit to your repo
  • Secrets still live in the app
Question 2

What is a unit of work, and what do you see of it?

2A · today

A branch

A Workspace is one branch with a sandbox, named by the branch.

  • Honest about what's underneath
  • Reads as git, not as the idea
2B

A titled Workspace

Same unit, but it gets a title from its first prompt. The branch can change over its life (a new branch after a merge) without renaming it.

  • Smallest change that reads as work
  • Fits Claude's thread titles
  • Still a separate list from the canvas
2C

A group on the canvas

The group is the Workspace. Making a group makes a sandbox. The sidebar lists groups, so the canvas and the list are the same thing. Builds on #868.

  • One object instead of two
  • Very spatial, very Screenplay
  • Frames from two Workspaces side by side need a mixed group
2D

A chat

The sidebar is a list of chats, like a Claude project. Each chat owns its sandbox, and its frames are what it produced. Terminals stay tabs of a chat.

  • The mental model people already have
  • Canvas chat sits on top naturally
  • Two chats in one sandbox gets harder
2E

A task across branches

A Workspace is a task. Its agent opens branches in any repo as it sees fit, like a Claude Code thread that opens two PRs.

  • Cross-repo work is one task
  • One sandbox per branch, costs multiply quietly
  • Frames need a checkout picker again, a later change to the address bar
2F

A version of a frame

No Workspace in the UI. You select a frame and choose Try another version. Versions stack on the frame like variants, and each one is a sandbox underneath.

  • Designer vocabulary, no git at all
  • Comparing is built in
  • A version spanning many screens is hard to show
Question 3

How much of the branch do you see?

3A · today

Everywhere

Sidebar, chat picker, frame labels and the address bar all show the branch.

3B

In the details

A hover card and the Workspace menu's Git group show repository, branch and base.

3C

Only as PR status

You see the PR (open, merged, failing) and never the branch name, unless you open it on GitHub.

3D

Managed by the agent

You never deal with branches. You ask the agent to ship, and it opens a PR. Rebase and rename go away.

Putting them together

Four coherent directions

Leaning here1B + 2B + 3B#868–#872 continue

I. Claude project

The canvas is the project. Repositories go to Canvas settings, the sidebar lists titled Workspaces with status, the Canvas chat sits on top, and the branch lives in the details.

Closest to what the Canvas Coordinator work already decided. The frame-label chain keeps going; its pills show a title instead of a branch later.

1B + 2D + 3C#868–#872 continue

II. Just chats

The same shape as I, one step further. The list is chats, not Workspaces. A chat's frames are its output. The word “Workspace” mostly disappears from the UI.

Cleanest mental model. The open question is what the Workspace pill on a group says when there are no Workspaces, probably the chat's title.

1D + 2C + 3BBuilds on #868

III. Figma-style

Projects live on the home screen and hold settings and canvases. Inside a canvas, groups are Workspaces, so there's no separate Workspace list at all.

Most spatial, and it fixes setting up a repo on every canvas. It's the biggest change to home and to folders.

1C + 2F + 3DReworks frame labels later

IV. Versions

One repo per canvas, no Workspaces or branches in sight. You make versions of frames and ship the one you like.

The most designer-friendly and the furthest from today. Frame labels shipped in #868–#872 would need reworking afterwards, because frames stop belonging to groups' Workspaces.

What happens to the frame-label chain

#868–#872 are landing now, whatever comes of this. They give groups a Workspace and add a Workspace switcher to the address bar. Under I, II and III that stays as built, with the pill showing a title instead of a branch. Only IV, and 2E on its own, would change what a frame points at, so only those would mean reworking the labels afterwards.
