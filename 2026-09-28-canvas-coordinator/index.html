Canvas Coordinator

A chat that works on the whole canvas instead of one Workspace or one document. It can see every Project, Workspace, frame and document in the canvas, rearrange them, start new Workspaces, and hand work to the agents already running in them.

Proposed destination

A product spec (PRD) for a v1 Canvas Coordinator that /to-tickets can slice straight into issues. We get there by answering the decision tickets on a wayfinder map, one at a time, starting with the questions at the bottom of this page.

The repo's wayfinder skill says the destination gets named with you first, then the map issue and its decision tickets are filed. Nothing is filed until you agree on the direction.

What exists today

The pieces a coordinator would build on

Screenplay already has most of the plumbing. The gap is a chat whose target is the canvas itself, plus a set of canvas tools that run on the server.

PieceHow it works nowWhat it means for a coordinator
Chat Targetslib/agent/chat-target-kinds.tsA chat talks to a Workspace's sandbox or to a document. The target picks the system prompt and the tools.The registry was built for new kinds. "Canvas" becomes a third target kind with its own tools.
Canvas Operationslib/canvas/ops.tsOne module holds every structural write: create Workspace, frames for routes, documents, move, merge groups, remove.It takes plain Yjs collections, and the server already has mutateRoomDoc. The coordinator's tools can reuse the same verbs server-side, so canvas invariants hold.
Workspace creationapp/api/branch/createThe client writes the Workspace record, then this route provisions the sandbox and can seed the first chat.A server-side path already exists. The coordinator can fan out N Workspaces with seed prompts.
Engineslib/agent/acp/Hosted chats use the in-process loop. The desktop build runs a harness (Claude Code, Codex) over ACP, with its working folder set to the Workspace's worktree.Harness sessions start with mcpServers: [], so a harness can't reach canvas tools today. A desktop coordinator needs a Screenplay MCP server, and a working folder that isn't a Workspace.
Plan reviewsubmit_plan toolThe agent proposes a plan, the loop pauses, and the user approves or rejects it in the panel.A natural approval step before a fan-out ("I'll create these 3 Workspaces").
Terminal TabsTerminalTabDataA harness running in a PTY, per user. Scrollback is never stored and nothing enters the chat store.A coordinator can't read or steer a terminal-hosted harness without new plumbing. This is a real gap, since terminals are used as chats.
Frame Captureslib/thumbnail/Each ready frame gets a stored screenshot for the home thumbnail.The coordinator could look at frames to compare variants side by side.
What it could do

Five levels of control

Each level needs everything to its left. The v1 scope is a cut somewhere along this line.

1

See

Read the whole canvas: Projects, Workspaces and their state, frames, routes, documents, PR status.

"What's blocked right now?"
Read tools only
2

Arrange

Add, move, group and label frames and documents.

"Put every checkout frame side by side at mobile and desktop."
Canvas Operation tools
3

Spawn

Create Workspaces with seed prompts and place their frames.

"Try three hero designs in three Workspaces."
Server-side Workspace creation
4

Steer

Send messages to Workspace agents, wait for them, read and compare the results.

"Tell the two losers to stop, and have the winner fix lint."
Cross-chat send and read
5

Ship

Open PRs, clean up Workspaces, write a summary document.

"Open a PR for the winner and remove the other two."
Destructive actions, confirms

Design forks

The main decisions and their tradeoffs

AWhere the coordinator lives

RecommendedA Canvas target in the chat panelReuses tabs, the composer, plan review and history. One new switcher entry.You can't watch a Workspace chat and the coordinator at the same time.
A floating command bar on the canvasClose to the work and quick for one-off layout commands.It would be new floating chrome, has no history, and is a poor fit for long runs.
A second docked panelCoordinator and Workspace chat are visible side by side.A big layout change. It crowds the canvas and goes against the preference for the existing UX.

BHow it gets work done in Workspaces

RecommendedDelegate through Workspace chatsEvery step is visible where you already look. Each agent keeps its own context, and you can step in at any time.Needs cross-chat send, wait and read, and something that watches for results.
Do the work itselfSimplest. One agent with file tools for every sandbox.One context fills up fast, there's no parallelism, and Workspace chats don't show what happened.
Hidden subagentsParallel and tidy.The work is invisible on a canvas whose whole point is showing work.

CWhat runs it

In-process loop onlyFastest to build. Canvas tools are plain AI SDK tools.Doesn't work on desktop, where chats are harness-backed.
RecommendedOne tool set, exposed two waysCanvas tools defined once, served as AI SDK tools and as a Screenplay MCP server passed to harness sessions. It works on both builds.An MCP server and its auth to build, plus a working folder for a session that has no Workspace.
Canvas CLI for any terminalAny harness in any Terminal Tab can drive the canvas, so your own Claude Code becomes the coordinator.No structured chat, so it can't show status cards or plans. Could come later on top of the same tools.

DHow much it does without asking

Ask before every changeSafe.Tedious for layout moves you can undo.
RecommendedTieredLayout changes happen right away. A fan-out goes through plan review first. Anything destructive (remove Workspace, delete branch, Recreate) always gets a confirm.Tiers need to be defined per tool.
Fully autonomousWalk away and come back to results.It can spend sandboxes and model budget fast, and mistakes are hard to undo.
Round 1 · answer by number

Questions for Zack

Q1

What's the destination of this map?

The options are a PRD ready for /to-tickets, a working prototype to react to, or just a locked-in direction with the build planned later.

A PRD for v1, with a throwaway prototype ticket on the way if the UI feels uncertain.

Q2

What's the first job you'd hand it?

  • Fan out: try N approaches in N Workspaces and compare them.
  • Status: tell me what every Workspace is doing and what's blocked.
  • Arrange: lay out the canvas for me.
  • Cross-repo: drive one feature across frontend and backend Projects.

Fan out plus status. They cover levels 1 to 4 and are the reason to have a canvas full of Workspaces at all.

Q3

Where does it live? (fork A)

A "Canvas" entry in the existing Workspace switcher, with its own tabs, like the mockup.

Q4

Does it delegate to Workspace agents, or do the work itself? (fork B)

Delegate through Workspace chats, as ordinary labelled messages you can take over.

Q5

Must v1 work on the desktop build, where chats are harness-backed? (fork C)

If yes, the canvas tools also ship as an MCP server that harness sessions receive, and the coordinator needs a working folder that isn't a Workspace worktree.

Yes. Desktop is where you work, so build the tools once and expose them both ways.

Q6

What about Terminal Tabs running a harness?

The coordinator can't read or steer them today. Should v1 treat them as out of reach (it sees they exist and can open one), or must it be able to talk to a harness running in a terminal?

Out of reach in v1: it can see and open them but not steer them. Steering them goes in the fog for later.

Q7

How much does it do without asking? (fork D)

Tiered. Layout changes happen right away, fan-outs go through plan review, and destructive actions always confirm.

Fog

Later questions we can't pin down yet

Waiting and waking. How the coordinator learns that a Workspace agent finished: polling, run-state events, or a turn that resumes itself.
Undo. Server-side writes have their own Yjs origin, so your ⌘Z wouldn't undo the coordinator's layout changes.
Multiplayer. On hosted canvases, whose identity and budget pay when the coordinator spawns Workspaces for a shared canvas.
Seeing frames. Whether comparing variants uses stored Frame Captures or fresh screenshots, and at which sizes.
Naming. The code term (a new Chat Target kind) and the UI label ("Canvas", "Coordinator", something else) for CONTEXT.md.
Limits. Caps on how many Workspaces one request may create, and what happens when a sandbox fails to boot mid fan-out.
