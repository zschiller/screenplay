Problem
A Document becomes text three independent ways (a hand-written Yjs walker for reads, a server schema without mentions for writes, and comment line counting), and none matches the editor's schema.
Solution
One module over the editor's own extension list, built on Tiptap's MarkdownManager in both directions, with mentions written as [@label](mention:chat/<id>) as the composer already does.
Wins
  • Locality: a node type is one edit
  • Interface is the test surface: one round trip per node
  • Deletes the walker and the unused renderMarkdown
  • Leverage for comment line numbers
Bug, confirmed by readingappend_to_document_body reads the body with fragmentBodyToPlainText (mentions come out as @label) and rewrites the whole body through a schema with no mention node (document-tools.ts:146–155, fragment-text.ts:176–181). Mention a chat, Document or Mockup in a Document, then ask its chat to add to it: every pill becomes plain text that no longer follows renames.
Bug, confirmed by readingread_document gives an agent each mention's label from when it was inserted, with no kind or id (fragment-text.ts:265–272), while the pill on screen shows the current name. After a rename the agent sees a name that no longer resolves, and it can't tell a chat from a Document.
Evidence
  • 2600b62 (images) touched four places for one node: DocumentImage.renderMarkdown, the image branch in collectNode, liftImagesFromParagraphs, markdownExtensions.
  • Deletion test: DocumentImage.renderMarkdown (document-image.ts:14–20) is never called, because nothing calls MarkdownManager.serialize.
  • Likely, not run: collectNode uses Y.XmlText.toString(), which writes formatting as <bold>…</bold>, so agents read marks as XML tags. The tool description already admits the append "flattens inline marks".
  • getLineNumbers (document-comments.ts:52–99) says it matches "what an LLM sees" but counts one line per block, while the walker adds blank lines and image lines.
  • fragment-text.test.ts has no case for marks or mentions.

Problem

Solution
One module takes a Mockup and the chats and answers which chat it is and whether this viewer's tap counts, with askForKnob, draft, question and answer; the Mockup layer gets it from context instead of four props.
Wins
  • Locality for the owner rule and the viewer gate
  • Leverage: the next verb is one entry
  • Routing tested with fake stores; untested today
  • Canvas root sheds ~90 lines
Bug, confirmed by readingask_question is in every chat and its description says a mockup_id lets the page show and answer the question (question-tools.ts:24). The page only reads questions from the Mockup's own chat transcript (use-mockup-question.ts:27–41, mockup-layer.tsx:363). When the Coordinator or another Sketch chat asks about a Mockup, the card links to it but the page never sees the question.
Evidence
  • 0075d33 (draft) and 60f5bf2 (answer) both edit postmessage-protocol.ts, sandbox-bridge/index.ts, mockup-layer.tsx, canvas-member-layer.tsx, canvas.tsx and the mockup-tools.ts description.
  • Two routing implementations: openMockupChat (canvas.tsx:1474–1500, via layerOwner) and handleAnswerFromMockup (:1531–1553), which opens owner.chatId but sends to raw ownerChatId, and sends a Mockup with no owner to the Coordinator, commented "The Coordinator made it". The Coordinator can't make Mockups (room-chat-target.ts has no Mockup tools).
  • Two viewer gates with opposite rules for a live page: draftFromViewer (mockup-layer.tsx:312) and canAnswer (:364). Only the draft gate is tested.
  • Messages arrive two ways: drafts through the live page's app events, questions through a second page.port subscription.
  • chat-draft-source-store.ts copies the skeleton of chat-quote-store.ts.
