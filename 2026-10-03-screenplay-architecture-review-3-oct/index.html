Problem
Which tools a Chat Target kind has, on which Engine, and what its prompt calls them, takes six modules to answer, and they already disagree.
Solution
Each Chat Target kind declares its tools once, with annotations attached; the in-process turn, the MCP route and the prompt all read that one list.
Wins
  • Locality: a tool is added in one place
  • Leverage: route and sandboxTurn shrink to "toolset for this target"
  • Test: MCP and in-process toolsets equal per kind
  • Deletes the unused half of ChatTargetSpec and its casts
Bug, confirmed by readingThe Workspace prompt (config.ts:83–111, 181) names submit_plan, run_command, create_pr and read_skill bare. A harness gets that whole prompt (acp-engine.ts:262) but the MCP route's Workspace branch (route.ts:84–110) serves none of them. A Claude Code Workspace chat is told "always use create_pr, never gh pr create" and has no create_pr.
Evidence
  • The Workspace toolset is assembled by hand three times: tools.ts:266–277, toolset.ts:49–58, route.ts:89–110; annotations listed again at route.ts:111–119, 143–149.
  • read_document is annotated twice (document-tools.ts:202, sketch-tools.ts:70).
  • 8 of 12 commits touching the MCP route since 30 Sep also touched 2–5 of config / toolset / tools / sketch-tools / chat-target-kinds (d96932eb, 27f29c92, ac7e369a, bf2e88ad, 48324895, c4a10bd3).
  • Deletion test on ChatTargetSpec: loadContext, buildSystemPrompt, buildTools (chat-target-kinds.ts:121–160) are never used in production; sandboxTurn re-implements them (turn-launch-live.ts:484–575); room and sketch turns cast through as unknown as never.
  • Smaller gap: route.ts:89 wraps tools in withRedactedOutput without secrets, so MCP tool output such as dev server logs reaches a harness unscrubbed (low impact locally, where the harness can read .env anyway).

Solution
